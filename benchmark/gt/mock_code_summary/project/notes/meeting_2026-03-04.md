## 1. 배경 정리

- 과제: Java 함수 본문을 입력으로 받아 한 문장짜리 요약(docstring 첫 문장)을 생성한다.
- 기존 검색 증강 방법(RetroSum)은 여러 프로젝트를 합친 전역 코퍼스에서 이웃 함수를 찾는다. 이웃이 전혀 다른 프로젝트에서 오면서 네이밍 규칙이 달라지는 문제가 자주 보였다.
- 같은 저장소 안의 함수는 도메인 용어와 명명 규칙을 공유하므로, 검색 범위를 저장소 안으로 좁히는 쪽이 더 유리할 것이라는 의견이 나왔다.

## 2. 주요 결정 사항

1. **저장소 범위 검색 모듈 추가 (확정)**
   - 같은 저장소 안에서 질의 함수와 가장 비슷한 함수 k개("형제 함수")를 찾는 모듈을 핵심 신규 모듈로 추가한다.
   - 저장소마다 별도 인덱스를 만들고, 전역 검색은 하지 않는다.
   - 이 모듈의 출력을 `src/reposum_model.py`의 인코더 뒤에 더해서 디코더가 사용하도록 한다.
2. **검색 개수 k = 4로 시작 (확정)**
   - 이후 k 값을 바꿔 보는 실험은 나중에 진행한다.
3. **누수 방지 규칙 (확정)**
   - 질의 함수 자신은 인덱스에서 제외한다.
   - 질의보다 나중 커밋에서 만들어진 함수도 제외한다.
   - 시간 순서를 지키지 않으면 테스트 성능이 과대평가될 수 있다는 점을 모두 확인했다.
4. **형제 함수의 표현 (확정)**
   - 형제 함수는 "코드 + 요약" 조합을 공유 인코더로 함께 인코딩한다.
5. **입력 길이 (확정)**
   - 소스 코드 최대 길이는 400 토큰, 요약 최대 길이는 48 토큰으로 한다.
   - 선행 연구처럼 512 토큰까지 쓰면 학습 비용이 크게 늘어난다.

## 3. 베이스라인 선정

- 선정 결과: Transformer, RetroSum, CodeSibling 세 가지.
- 이유
  - Transformer: 검색을 쓰지 않은 기본선이다. 검색 효과를 재는 기준점이다.
  - RetroSum: 검색 증강 요약의 대표 선행 연구다. 전역 검색과 연결 방식 차이를 보여 준다.
  - CodeSibling: 같은 파일 또는 패키지의 형제 함수를 쓰는 가장 가까운 방법이다. 우리 아이디어와 직접 비교가 된다.
- 초기 초안에는 Transformer와 CodeSibling만 있었다. RetroSum이 빠져 있다는 지적이 있어 추가했다.
- 한지우가 세 베이스라인의 실행 환경과 학습 설정을 맞추는 작업을 맡기로 했다.

### 데이터 분할 기준 (정하늘)
- intra_repo: 저장소 안에서 시간 순으로 80/10/10을 나눠 학습, 개발, 테스트에 배분한다.
- cross_repo: 저장소 단위로 나눠 학습에 보지 않은 저장소에서 평가한다.
- 데이터 규모: 자바 저장소 1,240개, 함수-요약 쌍 약 31만 2천 개(중복 제거 후).

## 5. 열린 질문 (다음 미팅에서 결정)

- 검색 인코더를 처음부터 함께 학습할지, 사전 학습된 인코더를 고정할지.
  - 임시 결정: 1차 실험은 사전 학습 인코더를 고정하고, 이후 검색 손실을 추가해 공동 학습을 시도한다.
- 양성 샘플 정의: 호출 그래프에서 이웃 관계를 공유하는 함수를 양성으로 본다는 안이 나왔다. 음성은 같은 배치 안의 같은 저장소 함수로 한다.
- 게이트 융합과 단순 연결 중 무엇을 본 모델로 할지. 현재는 게이트 융합을 기본으로 하고, 단순 연결은 비교 실험으로 남긴다.
- 학습 설정(옵티마이저, 학습률, 배치 크기, 에폭 수, 시드 등)은 공통 설정 파일로 관리하고 실험마다 값을 바꾸지 않는다.
